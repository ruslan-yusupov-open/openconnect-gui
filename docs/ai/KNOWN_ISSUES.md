## Архитектура, стиль, тесты и документация

Замечания 3.2–3.3 применимы качественно: MainWindow совмещает несколько обязанностей, передача владения неочевидна, диалоги дублируют синхронизацию. Число строк из новой ветки сюда не переносится. Рефакторинг выполнять отдельными малыми задачами после дефектов, а не массовой заменой синтаксиса.

По пункту 3.4: в исходной базе нет собственных unit/integration test targets; отключение тестов внешней spdlog не равно наличию тестов приложения. В этом PR добавляется только изолированная регрессия R6. Проверки всего GUI, secure storage и потоков остаются в плане.

По пункту 3.5: пути документации отличаются (`docs/dev_commandLine.md`, `docs/sw_requirements.md`), указаны исторические версии и пути. Новые документы объясняют ограничения сборки; они не утверждают, что весь старый toolchain проверен. Пользовательскую инструкцию управления сохранёнными секретами нужно дописать вместе с реализацией новой функции.

## Очерёдность дальнейших PR

1. Удалить секреты из логов и закрыть открытое сохранение при ошибке защиты; отдельно проверить парные API освобождения сертификатов.
2. Исправить синхронизацию диалогов и завершение worker с проверками отмены и сроков жизни.
3. Реализовать [безопасное сохранение пароля](CREDENTIAL_STORAGE.md), включая удаление и миграцию, после закрытия рисков хранения.
4. Исправить proxy URL и остальные подтверждённые дефекты; затем точечно разделять обязанности крупных классов.

При изменении статуса указывай коммит/PR, тест и результат. Не отмечай весь пункт R4 закрытым только после защиты обычного пароля: приватный ключ и OTP seed требуют отдельной проверки.
